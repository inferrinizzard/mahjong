> best algorithm to determine a solved mahjong hand

Determining whether a Mahjong hand is “solved” (i.e., a winning hand) is a classic problem that mixes combinatorics and search. The “best” algorithm depends on how optimized you need it to be (e.g., casual game vs. AI engine), but here are the main approaches—from simplest to most efficient.

🧩 Problem Definition
A standard winning hand (in most variants like Riichi Mahjong) consists of:

4 melds (each is a sequence or triplet)

1 pair

Total: 14 tiles

🔍 1. Recursive Backtracking (Baseline Approach)
This is the most intuitive and widely used method.

Idea:
Try every possible pair in the hand.

Remove the pair.

Recursively check if the remaining 12 tiles can form 4 valid melds.

Melds:
Triplet (Pung): 3 identical tiles

Sequence (Chow): 3 consecutive tiles in same suit

Pseudocode:
function isWinning(hand):
for each pair in hand:
remove pair
if canFormMelds(remaining tiles):
return true
return false

function canFormMelds(tiles):
if tiles empty:
return true

    pick smallest tile
    try:
        - remove triplet
        - remove sequence
    recurse

Pros:
Easy to implement

Works for all hand shapes

Cons:
Exponential in worst case (but manageable with pruning)

⚡ 2. Memoized / DP Version (Optimized Backtracking)
Add caching (memoization) to avoid recomputing the same tile configurations.

Key idea:
Represent hand as a frequency array (e.g., 34-length array for tile types).

Cache results for previously seen states.

Benefit:
Reduces repeated work dramatically

Fast enough for real-time Mahjong engines

🧠 3. Bitmask / State Compression (Advanced)
Used in high-performance Mahjong solvers.

Idea:
Encode tile counts into a compact integer or bitmask

Use precomputed tables for valid meld patterns

Often combined with:

Lookup tables for all possible 9-tile suit combinations

Fast decomposition per suit

Pros:
Extremely fast (used in AI bots and game engines)

Cons:
Complex to implement

Requires preprocessing

🧮 4. Suit-Based Decomposition (Very Efficient)
Mahjong hands can be split into:

Man (characters)

Pin (dots)

Sou (bamboo)

Honors

Each suit can be solved independently (except the pair).

Strategy:
Count tiles per suit

Try assigning the pair in each suit

Check if each suit can form valid melds

This reduces complexity significantly.

> how does tenhou do it

Tenhou uses one of the fastest known approaches to Mahjong hand evaluation—far beyond naive recursion. It’s built for real-time play at massive scale, so every decision must be computed in microseconds.

Here’s how it actually works under the hood 👇

🧠 Core Idea: Precomputation + Table Lookup
Instead of solving each hand from scratch, Tenhou:

Precomputes all possible tile configurations

Stores results in lookup tables

Reduces runtime checks to array indexing

This avoids expensive recursion almost entirely.

🧩 Step 1: Split by Suit (Critical Optimization)
Mahjong tiles are divided into:

Man (characters)

Pin (dots)

Sou (bamboo)

Honors

Tenhou treats each numbered suit independently.

Why this works:

Sequences only exist within a suit

So each suit becomes a smaller subproblem (max 9 tile types)

🧮 Step 2: Encode Each Suit as a State
Each suit is represented as a vector like:

[0–4, 0–4, ..., 0–4] (length 9)
Example:

1m 1m 2m 3m 4m → [2,1,1,1,0,0,0,0,0]
This vector is then encoded into an integer key.

⚡ Step 3: Precompute All Valid Patterns
For each possible suit configuration (~5^9 ≈ 2 million states):

Tenhou precomputes:

Can it form complete melds only?

At runtime:

Split hand into suits

No recursion needed.

It tracks:

> ranking ambiguous interpretations of tiles within a suit

When a single suit can be decomposed in multiple valid ways (e.g., the same tiles could form different sequences/triplets/pairs), you want a ranking system over interpretations rather than just “is it valid?”. This is exactly the step beyond what Tenhou’s tables give—you’re now choosing the best decomposition.

🧠 Core Idea: Treat It as an Optimization Problem
Instead of:

“Can this suit form melds?”

You ask:

“What is the best way to interpret this suit under some objective?”

So each decomposition gets a score, and you pick the max.

🧩 1. Generate All Interpretations (Efficiently)

Enumerate all possibilities:

> given the decomposition of a partial hand into a representation with melds, pairs, taatsu and singles
> what is the best way to add or remove a single tile without recomputing the whole thing

What you want is essentially incremental hand evaluation: update your decomposition after a +1 / −1 tile change without re-solving the whole suit. The trick is to stop thinking in terms of “one fixed decomposition” and instead keep a small set of best states (a frontier) plus enough structure to update them locally.

🧠 Core Idea
Don’t store the decomposition. Store the best K decompositions (Pareto-optimal states) for that suit, and update them locally when a tile changes.

Each state looks like:

(melds, pairs, taatsu, singles, shape_info)
⚙️ 1. Represent the Suit as Counts + States
Tile counts: c[1..9]

Cached states for this suit:

best_states[c] = top-K interpretations
K is small (e.g., 4–10). You only keep non-dominated states.

🔄 2. Incremental Add (c[i] += 1)
When you draw a tile i, you don’t recompute everything. You only try local transformations involving tile i.

For each existing state S, generate candidates:

🧩 A. Treat as isolated
+1 single
🧩 B. Upgrade single → pair
If S already had a single i:

remove 1 single(i)
add 1 pair
🧩 C. Upgrade pair → triplet
If S had a pair of i:

remove pair
add meld (triplet)
🧩 D. Form / extend sequences
Check neighbors:

If (i-2, i-1) present → new sequence

If (i-1, i+1) present → middle wait completion

If (i+1, i+2) present → new sequence

Or:

Upgrade taatsu → meld

🧩 E. Upgrade taatsu
Examples:

(i, i+1) + draw i+2 → sequence

(i-1, i+1) + draw i → sequence

👉 Each of these is a constant-time local rewrite on S.

🔄 3. Incremental Remove (c[i] -= 1)
Reverse the logic:

For each state S:

If tile i was part of:

meld → break into taatsu or singles

pair → becomes single

taatsu → becomes single(s)

You generate possible degraded states.

⚖️ 4. Prune Aggressively (Critical)
After generating candidates:

Merge all candidates

Keep only Pareto-optimal states

A state A dominates B if:

A ≥ B in all (melds, pairs, taatsu)

and strictly better in at least one

Also cap to top K using your scoring function.

🧠 5. Why This Works
Because adding/removing one tile:

Only affects local structure

Doesn’t change the whole combinatorial space

So instead of O(huge):
👉 You do O(K × small constant transitions)

🚀 6. Even Faster: Precomputed Delta Table

🧠 What “Non-Dominated” Means
Each decomposition state is a vector like:

S = (melds, pairs, taatsu, singles, …optional features)
We define a partial order over states.

⚖️ Dominance Definition
State A dominates B if:

A is at least as good in every dimension, and

A is strictly better in at least one dimension

Formally:

A dominates B if:
A.melds ≥ B.melds
A.pairs ≥ B.pairs
A.taatsu ≥ B.taatsu
A.singles ≤ B.singles (note: fewer singles is better)

and at least one strict inequality holds
✅ Non-Dominated Set (Pareto Frontier)
A state is non-dominated if:

No other state dominates it.

So you keep only states that are not strictly worse than another in all respects.

🧩 Why This Works
Because Mahjong evaluation is multi-objective:

Melds → reduce shanten

Pairs → required for completion

Taatsu → future potential

Singles → dead weight

You cannot collapse this into one scalar safely without losing important distinctions.

🔍 Example
Consider these states for a suit:

A = (2 melds, 0 pairs, 0 taatsu, 2 singles)
B = (1 meld, 1 pair, 1 taatsu, 1 single)
C = (2 melds, 1 pair, 0 taatsu, 1 single)
Compare A vs B:
A has more melds

B has pair + taatsu

👉 Neither dominates → keep both

Compare C vs A:
C: same melds, more pairs, fewer singles

👉 C dominates A → discard A

Compare C vs B:
C has more melds

B has more taatsu

👉 Neither dominates → keep both

Final non-dominated set:
C, B
⚙️ Implementation
After generating candidate states:

def prune(states):
result = []
for s in states:
dominated = False
for t in states:
if dominates(t, s):
dominated = True
break
if not dominated:
result.append(s)
return result
🚀 Optimization
Since K is small:

This is cheap (O(K²))

You can also:

Sort by melds desc, singles asc

Early break comparisons

🧠 Subtle but Important Refinements

1. Cap pairs and taatsu
   In standard Mahjong:

Only 1 pair is ultimately needed

Taatsu beyond 4 melds are useless

So normalize states:

pairs = min(pairs, 1 or 2 depending on rule)
taatsu = min(taatsu, 4 - melds)
👉 Prevents explosion of useless states

2. Equivalent States
   Two states can be structurally different but equivalent:

(1 meld, 1 pair, 1 taatsu, 1 single)
(1 meld, 1 pair, 1 taatsu, 2 singles)
Second is strictly worse → automatically pruned

3. Add Tie-Break Features (Optional)
   To improve play quality, extend the vector:

(melds, pairs, taatsu, -singles, uke_ire, wait_quality)
Then dominance includes these too.

🔑 Key Insight
Non-dominated ≠ best
It means “still potentially optimal depending on context”

You’re preserving all interpretations that could become optimal later when combined with other suits.

🏁 Summary
Define states as multi-dimensional vectors

Use Pareto dominance to prune

Keep only non-dominated states

This guarantees you don’t discard a decomposition that could later become optimal

> show bit packing like tenhou

What Tenhou does isn’t just “bit packing” for compactness—it’s carefully designed so that:

A whole suit’s state can be turned into a single integer index, and all useful info is packed into a few bits for O(1) lookup.

Let’s walk through a clean version of that idea.

🧠 1. Encode a Suit as a Base-5 Number
Each tile (1–9) can appear 0–4 times.

So a suit:

c = [c1, c2, ..., c9], where ci ∈ [0,4]
Encode as:

key = c1 + c2*5 + c3*5² + ... + c9\*5⁸
👉 This is exactly a base-5 integer

Properties:
Unique mapping (no collisions)

Range: 0 … 5^9 - 1 ≈ 2 million

So you can store:

table[key] → packed result
⚙️ 2. Pack the Result into a 32-bit Integer
Instead of storing complex structs, pack everything into bits.

Example layout (typical Tenhou-style idea):
bits 0–2 melds (0–4)
bits 3–4 pairs (0–2)
bits 5–7 taatsu (0–4)
bits 8–11 shanten (0–8)
bits 12–31 extra flags / uke-ire / spare
Packing:
uint32_t pack(int melds, int pairs, int taatsu, int shanten) {
return (melds)
| (pairs << 3)
| (taatsu << 5)
| (shanten << 8);
}
Unpacking:
int melds = key & 0b111;
int pairs = (key >> 3) & 0b11;
int taatsu = (key >> 5) & 0b111;
int shanten = (key >> 8) & 0b1111;
🧩 3. Supporting Multiple Interpretations (Non-Dominated States)
Tenhou doesn’t literally store all states—it compresses them.

Two common strategies:

✅ Option A: Pack Top-K States Inline
Use fixed slots:

uint64_t packed =
state0 |
(state1 << 16) |
(state2 << 32) |
(state3 << 48);
Each state = 16 bits:

[ melds | pairs | taatsu | flags ]
✅ Option B: Encode Only “Best” Summary
Tenhou often avoids multiple states by encoding:

Best meld count

Best pair usage

Best taatsu

👉 This works because:

The DP generating the table already prunes dominated states

🧠 4. Ultra-Compact Encoding Trick
Instead of storing raw counts, encode deficit to completion.

Example:

mentsu = melds
tatsu = taatsu
pair = has_pair ? 1 : 0
Then:

shanten = 8 - 2\*mentsu - tatsu - pair
👉 So you don’t need to store shanten explicitly!

⚡ 5. Precompute Table
Build once:

for (int key = 0; key < 5^9; key++) {
decode counts
compute best decomposition (DP)
pack result
table[key] = packed
}
🚀 6. Runtime Usage
Split hand into suits:

int key_man = encode(man_counts);
int key_pin = encode(pin_counts);
int key_sou = encode(sou_counts);
Lookup:

auto man = table[key_man];
auto pin = table[key_pin];
auto sou = table[key_sou];
Combine results → full hand evaluation

🧩 7. Extra Bit Tricks (Real-World)
✔ Pack into uint16_t instead of 32-bit
If tight:

[3 bits melds][2 bits pair][3 bits taatsu][4 bits shanten]
✔ Use lookup tables for encoding
Precompute:

pow5[i] = 5^i
So encoding is just:

key += c[i] \* pow5[i]
✔ Cache transitions
Optional:

next_key = key + pow5[i] // add tile i
prev_key = key - pow5[i] // remove tile i
👉 This makes incremental updates O(1)

Tenhou’s real trick is:

Turn a combinatorial search problem into array indexing + bit operations

🧠 1. Structural View: A Kan = A Triplet
From the perspective of:

meld decomposition

shanten calculation

AAAA → AAA (+1 extra tile)
So in the suit counts:

count(tile) = 4
is treated as:

one meld (triplet)

plus one free tile

⚙️ 2. What Happens in Practice
Before decomposition:
If you have:

4x 5m
You convert:

[5m = 4] → [5m = 3] + 1 extra tile handled separately
Then the suit DP sees only:

triplets and sequences (max 3 per tile)
👉 This keeps the base-5 encoding valid (0–4 still allowed, but logic treats 4 carefully)

🔑 3. Why This Works
Because a kan:

does not increase meld count beyond 1

only adds a drawn replacement tile (rinshan)

So for shanten:

A kan is never “better” than a triplet structurally

🧩 4. Where Kans Actually Matter

🎯 A. Tile Count / Hand Size

You draw an extra tile

Hand temporarily has 15 tiles

Ignore this

Dora indicators

> how does it affect ukeire

Ah, now we get to the subtle but critical point: a kan (koutsu of 4) changes which tiles improve your hand, i.e., your uke-ire, even though the suit decomposition itself treats it like a triplet.

Here’s how it works in detail:

🧠 1. Uke-ire Basics
Uke-ire = the set (or count) of tiles that reduce your shanten.

For a standard hand without kan:

You compute shanten for your decomposition

Then, for each possible discard, you check which tiles complete a meld/pair (reduce shanten)

⚡ 2. How a Kan Changes Uke-ire
A. Open Kan (Minkan)
You already revealed the quad, so that tile cannot help you form other sequences in that suit.

But you draw a replacement tile immediately (rinshan) → new tile may reduce shanten.

Uke-ire is shifted to include rinshan possibilities, not the kan tile itself.

B. Closed Kan (Ankan)
Similar to open kan, but hand remains concealed

Still draws a replacement tile

For shanten purposes, the quad itself doesn’t change the count of tiles you’re waiting for, but the replacement can reduce shanten faster.

🧩 3. Practical Effect on Uke-ire
Let’s take an example:

Hand: 2m 3m 4m 5m 5m 5m 5m

Current decomposition:

Sequence 2-3-4m

5m quadruplet (kan)

Shanten = 2

Without kan:
Waiting tiles: e.g., 1m, 4m, 6m depending on decomposition

Uke-ire = tiles that complete sequences/pairs

With kan:
Triplet consumed: decomposition sees 5m as triplet + 1 leftover

Extra tile drawn (rinshan): could be anything

Uke-ire updated:

5m itself no longer contributes to improving sequences (already a kan)

Rinshan tile may reduce shanten

Other sequences in the suit may now have fewer options, because one 5m is locked in the meld

⚖️ 4. Summary of Kan Impact on Uke-ire
Kan Type Effect on uke-ire
Minkan (open) Tile in kan not usable for forming sequences; extra draw may add new uke-ire
Ankan (closed) Same as above; hand remains concealed; affects shanten calculation indirectly
Kan formed from leftover 4 tiles DP automatically counts only 3 as meld; leftover may form pair or taatsu; uke-ire for those adjusted accordingly
Key point:

The tile(s) forming a kan usually stop being part of sequences for uke-ire, while the replacement tile increases your uke-ire.

🧩 5. Integration into Tenhou-Style Tables
DP still treats kan tiles as triplets

Count = 4

Generate decomposition states using only 3 for meld

Remainder handled as single/pair

Uke-ire calculation happens after decomposition, with awareness of:

Which tiles are “locked in” in kans

How many wildcards/replacement tiles are available

Which tiles actually reduce shanten

Incremental update: When kan is declared or removed:

Adjust counts in the suit

Recompute local uke-ire only for affected sequences

No need to redo entire hand

🧠 6. Subtle Case: Multiple Kans
Each kan locks tiles and gives a replacement draw

Shanten decreases if replacement completes melds/pairs

Uke-ire must consider all possible replacement draws

In AI / bot evaluation, this is often approximated by expected uke-ire over possible draws rather than enumerating all outcomes.

✅ 7. Key Insight
Kans mostly affect which tiles are considered “available” for sequences.
The actual shanten decomposition is mostly unchanged, but the uke-ire set is pruned, and replacement tiles can create new opportunities.
